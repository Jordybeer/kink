## Bigger structural work (deferred, sketched in the proposal)

Not started. Listed in descending leverage. Each is its own multi-day chunk.

### A. Profile type system (Primary / Alternate / Partner)

- Current state: implicit. `pinnedProfileId` marks primary, `origin: "shared"`
  / `isImported` mark partner snapshots. UI gives no visual distinction.
- Proposed: three explicit types derived from those fields:
  - **Primary** — amber/warm "PRIMARY" badge, fully editable
  - **Alternate** — same person, different dynamic, fully editable
  - **Partner snapshot** — locked except private note, lock icon, import date
- Needs: `lockedAt: number` field added to `Profile` type, populated on QR
  import / backup restore.
- New `<LockField>` wrapper component for partner-snapshot fields:
  lock icon in label, `pointer-events: none` on the field, distinct visual
  treatment of the editable "Your note" field.
- Dutch copy: "Primair" / "Alternatief" / "Partner".

### B. Agreement archive (replace ContractSnapshot)

The highest-leverage change. Currently `ContractSnapshot` stores only counts:

```ts
{ matchCount, hardLimitCount, softLimitCount, discussCount, safeword }
```

This makes history permanently unreadable. You know you agreed on 34 kinks
in February — which ones? If either person updated their profile since,
the counts refer to a state that no longer exists.

Proposed:

```ts
interface Agreement {
  id: string;
  createdAt: Date;
  profileASnapshot: ProfileSnapshot;
  profileBSnapshot: ProfileSnapshot;
  sections: { shared: KinkId[]; limits: KinkId[]; discuss: KinkId[] };
  safeword: string;
  aftercareOptions: string[];
  signatures: { a?: string; b?: string };
  notes?: string;
  status: "active" | "archived" | "superseded";
  kinksVersion: number;   // for graceful degradation when KINKS evolves
}

interface ProfileSnapshot {
  profileId: string;
  name: string;
  role: string;
  entries: Record<string, Pick<KinkEntry, "status" | "statusGive" | "statusReceive" | "direction">>;
  capturedAt: Date;
}
```

Open questions to resolve before building:
- **Real localStorage budget.** Earlier hand-wave was ~480-800KB for 20
  agreements. Needs measurement: how dense are users' rated-kink sets?
  How long are comments? LZ-string compression worth it?
- **`KINKS` version drift.** Old snapshot may reference removed IDs.
  Render *something* ("3 archived kinks no longer in catalogue") and never
  crash.
- **Migration.** Existing `ContractSnapshot[]` becomes
  `LegacyContract[]` with a different type. Detail view renders only
  available count fields with note "saved without full kink data."
- **Dutch copy.** "Contract" → "Afspraak" or "Overeenkomst". The CTA
  on /compare still says "Contract" — leave that alone until this lands.

### C. Evolution view (replace timeline)

`CompatibilityTimeline` shows a line chart of contract-snapshot counts
over time. Useless for the questions people actually have. Replace with
a drift model — only possible once Agreements store full data (B above).

Three sub-views:
- **My drift** — per-profile kinks grouped by stability: Anchored
  (never changed), Trending ↑ (moved toward yes/willing recently),
  Receding ↓ (moved toward no/hard_no recently), Volatile (changed
  multiple times).
- **Compatibility drift** — per-pair score over time + category-level
  breakdown ("Bondage 87→91% improving", "Impact 72→45% diverging").
- **Turning points** — automatically detected shifts >10% category
  impact, shown as a list of dated events with what changed.

Open question: what counts as "change"? Status (yes→no) certainly.
Direction (give→both)? Comment edits? Volatility threshold?

one. Requires BottomNav reshuffle (Scenes currently has its own tab).

## Process notes for next session

Things I should have done and didn't:

1. **Write proposal copy in the product's language, not English.**
   "Agreement", "Mark discussed", "Set as Primary" — all wrong for a
   Dutch-first app. Translate the structural-work proposals into Dutch
   before building.
2. **Never ship a "redesign" commit that only does refactor.** The first
   `/compare` commit should have been labeled `refactor` not `design`.
3. **Run the AI-default check explicitly.** KinkSync's midnight theme
   IS the "dark dating app" default — fourth common AI look not in the
   frontend-design skill's enumerated three. Calling that out upfront
   would have changed the conversation earlier.
4. **Verify in browser before declaring a design ships.** The
   confetti-vs-masthead score mismatch was invisible until I took
   screenshots. Any visual change needs visual verification, not just
   passing tests.

## Suggested next move

**Highest leverage**: Start the Agreement data model (B in structural work
above). It's the linchpin — turns the contract history from a dead metadata
artifact into a real archive, enables the Evolution view (C), and anchors
the /history consolidation (D). Multi-day chunk; resolve the open questions
first (localStorage budget, KINKS version drift, migration path).

**Immediate scope**: Profile type system (A). Smaller entry point, no data
migration. Adds visual distinction (Primary / Alternate / Partner badges) and
locks imported partner fields — matches the UX direction of the tone-down pass.

**Editorial depth**: Once Agreement lands, add a second Cormorant italic anchor
(e.g., the Agreement detail view header or Evolution turning points summary)
so the masthead isn't isolated — the typeface becomes part of the page's
editorial voice, not a single flourish.
